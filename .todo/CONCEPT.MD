# Резюме проекта  
Предлагаемый продукт – это «Playwright для настольных приложений»: единый фреймворк автоматизации GUI настольных приложений разных платформ (Windows, Linux, macOS). Он сочетает идеи Playwright (локаторы на основе ролей и текстов, автопроверки готовности элементов, цепочки локаторов, инспектор) с адаптерами для Windows UI Automation (UIA), Linux AT-SPI и Java Access Bridge. Цели: упростить тестирование и RPA, обеспечить удобный API для работы со Swing, Qt, GTK, Win32, WPF, WinUI и другими технологиями. Команды разработчиков и QA смогут писать автоматические сценарии в единой парадигме независимо от платформы, используя Python API (или иной язык) по аналогии с Playwright. Такой фреймворк также будет полезен в задачах RPA и проверке доступности (accessibility), поскольку все поддерживаемые технологии имеют сходную модель: дерево элементов, роли, состояния и события.

## Цели и целевые пользователи  
- **Цели продукта:** объединить автоматизацию desktop-приложений в единый фреймворк с простым API. Поддержать кроссплатформенность (Win+Linux+Mac), различные UI-стэки (Java/Swing, .NET, Qt, Electron и т.д.) и сценарии (регресс-тестирование, RPA, тестирование доступности). Снизить количество дублей логики для разных платформ и ускорить создание скриптов за счет декларативных локаторов и автоожидания.  
- **Целевая аудитория:** QA-инженеры, автоматизаторы, DevOps/CI-специалисты, разработчики RPA-решений, специалисты по доступности и тестировщики desktop UI. Любые команды, которым нужно скриптовать взаимодействие с окнами и элементами GUI (например, тестирование кросс-платформенных Java-приложений, Electron-приложений или сервисов с графическим интерфейсом).  

## Сценарии использования  
- **Автоматизированное тестирование настольных приложений:** функциональное/регрессионное тестирование GUI-приложений (Java/Swing, Windows Forms/WPF, Qt/GTK, Electron, Qt/QML и др.), сценарии end-to-end. Унификация тестов: один и тот же код автоматизации подходит для разных ОС и фреймворков.  
- **RPA (Robotic Process Automation):** автоматизация рутинных задач (например, ввод в формы, навигация по меню, сценарии «кликни там — введи сюда»). Инструмент может выступать движком RPA для бизнес-процессов с десктоп-приложениями.  
- **Тестирование доступности (Accessibility Testing):** проверка доступности приложений для скринридеров. Так как фреймворк оперирует ролями и доступными именами элементов, его можно использовать для аудита ARIA-семантики и поведения экранных читателей.  
- **Инспектор/отладка (Inspector):** интерактивный инструмент (IDE-плагин или самостоятельный) для «захвата» локаторов. Пользователь наводит мышь на элемент приложения, видит дерево доступности и генерируется локатор наподобие `get_by_role("button", name="OK")`. По аналогии с Playwright Inspector такое средство значительно упростит написание скриптов.  

## Требования к API и функциональность  
- **Локаторы (Locator API):** методы `get_by_*`, подобные Playwright, ориентированные на доступность. Например: `get_by_role(role, name=None, **filters)` (роль элемента + опциональная видимая подпись), `get_by_text()`, `get_by_name()` (имя/заголовок), `get_by_automation_id()` (для UIA), `get_by_label()`, `get_by_placeholder()`, `get_by_tooltip()`, `get_by_class()`, `get_by_attributes()` и др. Важно поддержать фильтры: `checked=True`, `disabled=False` и т.п. (аналог `.filter()`/`.and_()` в Playwright). Все методы должны возвращать **Locator** (не элемент), т.е. лениво разрешать элемент при выполнении действия.  
- **Ленивое разрешение:** каждый вызов действия (`click()`, `fill()`, `check()` и т.д.) заново ищет свежий элемент по локатору. Это гарантирует, что при изменении UI (перерисовке) скрипт не «поймает устаревший» элемент. Подобная стратегия предотвращает flakiness.  
- **Автоожидания (Auto-wait):** встроенный механизм ожидания готовности элемента перед действием. Как и в Playwright, перед `click()` или `fill()` проверяются: элемент найден и единственный, **видимый** на экране, **стабилен** (не двигается, не анимируется), **получает события** (не перекрыт другими окнами), и **активен/доступен** (не задизейблен). Если элемент не готов, фреймворк будет ждать до тайм-аута и бросит ошибку по истечении времени. Это освобождает пользователя от явных пауз (никаких `sleep()` в коде).  
- **Assertions/Expect:** аналог Playwright `expect()`. Методы `to_be_visible()`, `to_have_text()`, `to_be_enabled()` и т.д. с авто-повтором (auto-retry) до выполнения условия. Например: `expect(locator).to_be_visible()` будет ждать, пока элемент не станет видимым, в противном случае — падение теста.  
- **Инспектор:** команда `codegen` или GUI, запускающая приложение и IDE-плагин. При наведении/клике строится локатор и код на Python. Например, нажатие на кнопку сгенерирует `app.get_by_role("button", name="OK").click()`. Также поддержка записи сценариев: генерация последовательности действий с локаторами и проверок.  
- **Работа с координатами:** методы для обхода ограничений доступности. Методы `bounding_box()` (получить рамку элемента), `click(coords=(x,y))` или `drag_to(other_locator)` для перетаскиваний. Это полезно, если элементов нет в дереве доступности или нужно кликнуть в определённой точке.  
- **Снимок дерева:** функция вывода текущего дерева элементов (например, `app.dump_tree()` или `window.dump_tree()`). Это поможет в отладке и инспектировании интерфейса, аналог DOM tree в браузере.  
- **Процессы/Окна:** интерфейс для работы с процессом и окнами. Например, `Automation.connect(process=pid)` или `Automation.connect(app_name="MyApp")` возвращает `Application` объект. Далее `app.window(title="Main")` получает главное окно по заголовку. Аналог `Browser` и `Page` в Playwright. Подсистема управления сессиями позволит переключаться между несколькими приложениями.  
- **Кроссплатформенный интерфейс:** единый API независим от backend. Код вида `locator = app.get_by_role("button", name="OK")` работает для Swing/Java (JAB backend), нативного Win32 (UIA backend) или GTK-Qt на Linux (AT-SPI backend). Все особенности платформы скрыты внутри адаптеров.  

Пример использования (Python):  
```python
from automation import Automation, expect

# Подключаемся к процессу приложения (например, уже запущенному или по пути exe).
app = Automation.connect(app_name="MyApp.exe")
# Находим главное окно по его роли и заголовку
window = app.get_by_role("window", name="Main Window")
# Заполняем форму
window.get_by_role("textbox", name="User").fill("admin")
window.get_by_role("textbox", name="Password").fill("secret")
window.get_by_role("button", name="Login").click()
# Проверяем результат
expect(window.get_by_text("Welcome, admin")).to_be_visible()
```
В этом примере `get_by_role`, `get_by_text` – локаторы по роли/тексту. Каждый `click()/fill()` автоматически ждёт, пока элемент появится и станет доступен (auto-wait).

## Архитектура  
Предлагаемая архитектура строится на трёх уровнях:

```mermaid
graph LR
    subgraph Automation Engine (API)
        A[Automation] --> B[Session/Application]
        B --> C[Window]
        C --> D[Locator]
        D --> E[ElementHandle]
        Automation --> K[Keyboard]
        Automation --> M[Mouse]
        Automation --> P[Clipboard]
        Automation --> I[Inspector]
    end
    subgraph Backend Adapters
        JAB[Java Access Bridge (Windows/Java)]
        UIA[UI Automation (Windows)]
        ATSPI[AT-SPI (Linux)]
        AX[macOS Accessibility API]
    end
    A -. Queries .-> JAB
    A -. Queries .-> UIA
    A -. Queries .-> ATSPI
    A -. Queries .-> AX
    JAB ---|Events| A
    UIA ---|Events| A
    ATSPI ---|Events| A
    AX ---|Events| A
```

- **Automation Engine (API):** сердцевина фреймворка. Содержит классы `Automation/Session`, `Application`, `Window`, `Locator`, `ElementHandle` (очень редко нужен, поскольку работаем через локаторы), а также сервисы `Keyboard`, `Mouse`, `Clipboard`, `Inspector`. Именно с их помощью пользователи пишут скрипты (см. пример выше). `Automation` управляет подключениями к приложениям (по PID или имени), а `Locator` – основная рабочая единица поиска элементов.  
- **Backend Adapters:** мосты к конкретным платформам. Для Windows это UIA (через COM) и для Java-on-Windows – Java Access Bridge (JAB). Для Linux – AT-SPI (через DBus, работает для GTK, Qt, Java, Electron). Для macOS – API Accessibility (AX API) и Cocoa. Каждый адаптер реализует интерфейс поиска элементов, получения свойств (role, name, bounds, state) и выполнения действий (invoke, setValue и т.д.). Engine не знает деталей протокола, обращается к адаптерам по абстрактным вызовам.  
- **Кэш объектов:** для повышения производительности можно кэшировать объекты из UI-дерева. Например, хранить дескрипторы или ссылки на объекты, чтобы не запрашивать у системы каждый раз. При этом нужно отслеживать события об изменениях (см. ниже) для актуализации кэша.  

Эта многослойная архитектура обеспечивает масштабируемость и расширяемость. Позже можно добавить новые адаптеры (например, для Android или web через Electron) без изменения внешнего API.

## Спецификация локаторов и фильтров  
Базовые методы поиска элементов (`Locator` API):  

- `get_by_role(role, name=None, **filters)`: основной метод. `role` – строка из списка ролей (например, `"button"`, `"checkbox"`, `"text"`, `"window"`, `"table"`, `"treeitem"` и др.), соответствующая контрольному типу UIA/AT-SPI. `name` – доступное имя (метка, заголовок) элемента. Фильтры: например, `checked=True/False`, `disabled=True/False`, `expanded=True/False`, `visible=True/False`, и т.д.  
- `get_by_text(text, exact=True)`: поиск по текстовому содержимому элемента (полностью или как подстрока, поддержка regex). Полезно для кнопок, меток, элементов списка.  
- `get_by_name(name)`: альтернативный поиск по имени/заголовку (если не хочется указывать роль).  
- `get_by_label(label)`: для форм, найти поле по его метке.  
- `get_by_placeholder(placeholder)`: искать текстовое поле по placeholder-тексту.  
- `get_by_tooltip(text)`: искать по тултипу (подсказке).  
- `get_by_automation_id(id)`: для UIA – по AutomationId (атрибут developer tools в WPF/WinUI).  
- `get_by_class(name)`: по классу/типу элемента (например, `Button`, `Edit`).  
- `get_by_attribute(attr="value")`: по любому свойству (например, `ControlType`, `AutomationId`, `AccessibleDescription`).  

**Цепочки локаторов:** методы поиска (`get_by_*`) доступны и на самом `Locator` или `Window`. Например:  
```python
btn = app.get_by_role("window", name="Settings") \
         .get_by_role("group", name="Network") \
         .get_by_role("button", name="Connect")
btn.click()
```  
Это аналог фрейма Playwright, но без понятия `<frame>` – просто фильтрация по дереву.  

**Lazy resolution (ленивость):** `get_by_*` возвращает Locator, а не конкретный элемент. Методы `click()`, `fill()` и т.п. у Locator при выполнении заново ищут элемент (как показано в Playwright). Поэтому изменения интерфейса не ломают цепочки.  

**Таймауты и повторы:** все поисковые и action-методы принимают необязательный `timeout`. По умолчанию действует глобальный таймаут (например, 30 с). При каждом вызове локатора будет предпринята серия попыток с задержками до истечения таймаута (auto-retry). Это существенно снижает хрупкость тестов.

**Пример локатора с фильтрами:**  
```python
# Найти ненажатую чекбокс «Подписаться»
locator = app.get_by_role("checkbox", name="Подписаться", checked=False)
locator.check()  # ожидание до появления и готовности, затем проверит чекбокс
```

Придерживаясь подхода Playwright, рекомендуется **приоритезировать локаторы по ролям и текстам**. Это соответствует восприятию интерфейса пользователем и скринридером. В боевых скриптах базовые локаторы могут комбинироваться фильтрами или дополнительными методами (`filter(has_text=...)` и т.д.) для точности. Например:  
```python
# Найти строку таблицы, содержащую «Продукт 2», и нажать «Добавить»
product = table.get_by_role("row").filter(has_text="Продукт 2")
product.get_by_role("button", name="Добавить").click()
```

## Auto-wait и Actionability для Desktop  
Перед любым действием фреймворк выполняет **проверки готовности элемента** (аналоги actionability checks Playwright):
- **Существование:** локатор должен разрешиться в ровно один элемент (иначе `NoSuchElement` или `AmbiguousLocator`).
- **Видимость (Visible):** элемент на экране (не скрыт, окно не свернуто).  
- **Стабильность (Stable):** элемент не меняет размеров и положения (например, нет анимации layout).  
- **Приём событий (Receives Events):** элемент не перекрыт другими окнами и может получать ввод (в том числе не закрыт модальными диалогами).  
- **Доступность (Enabled/Editable):** элемент не задизейблен, если требуется ввод или нажатие.  

Только когда все проверки пройдены, выполняется действие (`click`, `fill`, `check` и др.). Если что-то не готово, функция будет ждать до истечения таймаута и бросит ошибку.  

Например, `locator.click()` гарантирует, что перед кликом элемент существует, видим, активен и готов к получению событий. Это позволяет писать:  
```python
app.get_by_role("button", name="ОК").click()
```
без дополнительных `wait()` или `sleep()`. 

## События и кэширование  
Фреймворк может подписываться на события UI (например, изменение фокуса, изменения в дереве, нажатия). Это полезно для отзывчивости: можно реализовать обратные вызовы по аналогии с `page.on('click', handler)` в Playwright. Также события помогают поддерживать консистентность кэша.  

**Кэширование:** для ускорения работы стоит кешировать полученные объекты (дескрипторы окон, элементы). Например, при поиске окна по заголовку можно сохранить ссылку на окно до его закрытия. НВDA и другие продвинутые утилиты используют кэширование AccessibleContext (NVDA JABHandler) для снижения количества операций [※]. При поступлении события об изменении интерфейса фреймворк должен обновить или сбросить соответствующий кэш.  

## Инспектор/IDE-интеграция  
**Инспектор (Inspector/Codegen):** упрощает создание тестов. Схема работы аналогична Playwright Inspector: запускается приложение вместе с инспектором (или VS Code extension). При наведении курсора на элемент на экране инспектор показывает его свойства (роль, имя, класс, координаты) и автоматически генерирует локатор. Например, пользователь наводит на кнопку «ОК» – инспектор выводит `locator = app.get_by_role("button", name="ОК")`. Также есть функционал записи сценария: выполняя действия в приложении, инспектор генерирует код (Python) с этим локатором и действиями.  

**Визуальное выделение:** инспектор должен подсвечивать элемент на экране и его путь в дереве (аналог «Inspect.exe» для UIA). Наведение в IDE на локатор в скрипте могло бы также выделять элемент на запущенном приложении (при наличии соединения).  

**Интеграция с IDE:** возможна разработка плагина для VS Code или PyCharm, который запускает инспектор и сразу вставляет сгенерированный код в тест.  

## Минимально жизнеспособный продукт (MVP)  
**Функции MVP:**  
- Подключение к приложению (по PID или имени), базовая навигация по окнам.  
- Локаторы `get_by_role`, `get_by_text`, `get_by_name`.  
- Действия: `click()`, `double_click()`, `fill()`, `check()/uncheck()`, `focus()`, `press()`, `drag_to()`.  
- Базовый auto-wait (существование, видимость, enabled).  
- Простая архитектура с адаптером UIA (Windows) и AT-SPI (Linux).  
- Команда `dump_tree()` или `print_tree()` для вывода структуры GUI.  
- Пример кода-генератор для записи: базовая функциональность (например, CLI `automation codegen`).  
- Набор unit-тестов для ядра, демонстрация скриптов.  

**Приоритеты:**  
1. Работающий прототип на Windows (UIA) и Linux (AT-SPI).  
2. Надёжные локаторы и auto-wait (ключевые для удобства).  
3. Пример inspector (простой вывод в консоль локатора при клике мышью).  
4. Объединённый API без утечек платформенных деталей.  

**Оценка трудозатрат (примерно):**  
- Проектирование API и базового ядра: ~1–2 чел.-месяца.  
- Адаптер UIA (включая опыт поиска): ~2–3 чел.-месяца.  
- Адаптер AT-SPI: ~2–3 чел.-месяца.  
- Auto-wait и обработка исключений: ~1 чел.-месяц.  
- Inspector/Codegen (минимальная версия): ~1–2 чел.-месяца.  
- Тесты, документация, CI: ~1–2 чел.-месяца.  

**Риски и mitigations:**  
- *Различия в API:* UIA, AT-SPI и JAB имеют разные наборы возможностей. Решение: абстрагировать наиболее общие (дерево, роли, имя, действия), предоставить расширения там, где возможно.  
- *Стабильность локаторов:* динамические интерфейсы могут менять поведение. Решение: хорошая стратегия локаторов (роли + текст) и фильтров.  
- *Производительность:* обход больших деревьев может быть медленным. Решение: кэширование и события-инвалидации.  
- *Поддержка новых ОС/фреймворков:* на старте поддержка Windows/Linux, в планах macOS. Решение: модульная архитектура с добавлением backends.

## Примеры кода (Python)  
```python
app = Automation.connect(app_name="ExampleApp")
# Найти окно настроек и заполнить поля
settings = app.get_by_role("window", name="Настройки")
settings.get_by_role("textbox", name="Хост").fill("localhost")
settings.get_by_role("textbox", name="Порт").fill("5432")
settings.get_by_role("button", name="Подключиться").click()
# Убедиться, что подключились
expect(settings.get_by_text("Статус: подключено")).to_be_visible()

# Поиск в таблице: выбрать строку с текстом "admin"
table = app.get_by_role("table", name="Пользователи")
row = table.get_by_role("row").filter(has_text="admin")
row.get_by_role("button", name="Редактировать").click()
```
Каждый локатор (`get_by_role`, `get_by_text` и т.д.) возвращает **Locator**. Вызовы `click()`, `fill()`, `check()` автоматически ждут готовности элемента. Методы `has_text`, `filter` позволяют уточнять выбор по содержимому (подобно CSS-фильтрам в Playwright).  

## Сравнение с существующими решениями  
| Проект               | Поддержка ОС                 | Технологии UI                                    | Язык/API              | Особенности                                                                                                                                                     |
| -------------------- | ---------------------------- | ------------------------------------------------ | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Playwright** (web) | Все (браузеры)               | DOM/ARIA (веб)                                   | JS, Python, etc.      | Локаторы по ролям, auto-wait, инспектор. ТОЛЬКО веб.                                                                                                            |
| **Appium**           | iOS, Android, Windows, macOS | UI Automation (WinAppDriver), XCUITest, Espresso | JSON Wire (WebDriver) | Мобильная и настольная автоматизация. Поддерживает Windows через WinAppDriver, Mac через Mac2Driver. Сильный стек, но нет Linux.                                |
| **pywinauto**        | Windows                      | Win32, UIA (Windows)                             | Python                | Автоматизация Win32 и .NET приложений. Ищет окна/контролы по заголовкам, классам, AutomationId. Нет кросс-платформенности.                                      |
| **dogtail**          | Linux                        | AT-SPI (GTK, Qt, Java, …)                        | Python                | Использует AT-SPI, дружит с GNOME. Хорош для Linux, не работает на Windows/Mac. Похож на pywinauto, но для Linux.                                               |
| **LDTP**             | Linux, Windows, macOS        | AT-SPI (Desktop), Java Swing, Qt, …              | Python, C#            | Кроссплатформенный тестовый фреймворк. Поддерживает Linux/Mac/Win по AT-SPI и Java/Qt. Код на Python (LDTP) или C# (Cobra). Устаревший, но концептуально похож. |
| **pyjab**            | Windows (Java only)          | Java Access Bridge                               | Python                | Специализирован для Java/Swing. Тонкая обёртка JAB. Код основан на NVDA. Не покрывает другие UI-фреймворки.                                                     |

**Вывод:** Нет ни одного фреймворка, объединяющего все платформы. Playwright и Appium не покрывают Linux desktop. Pywinauto/dogtail сузки по ОС. PyJAB – только Java. Наш продукт заполняет «белую область»: единый API для всего десктопа.  

## Рекомендуемые источники и репозитории  
- **Playwright (официальная документация и исходники):** требования по локаторам, Auto-wait, инспектор.  
- **OpenJDK (Java Access Bridge):** файлы `AccessBridgeCalls.h`, `AccessBridgeCalls.c` (клиентская реализация).  
- **NVDA (JABHandler.py):** NVDA (экранный чтец) содержит обширный код поддержки JAB, включая кэширование и обработку событий.  
- **pyatspi (GNOME AT-SPI):** [GitLab](https://gitlab.gnome.org) – Python-биндинги для AT-SPI (используется в dogtail).  
- **dogtail:** [GitHub](https://github.com/vhumpa/dogtail) – пример использования AT-SPI для автоматизации Linux.  
- **pywinauto:** [ReadTheDocs](https://pywinauto.readthedocs.io) – Python-библиотека для Windows UI Automation.  
- **FlaUI:** [GitHub FlaUI](https://github.com/FlaUI/FlaUI) – .NET-библиотека над UIA (информация по ролям, AutomationId).  
- **Appium:** [Официальный сайт](http://appium.io) и [документация](https://appium.io/docs) – поддержка разных платформ.  
- **LDTP:** [Wikipedia](https://en.wikipedia.org/wiki/Linux_Desktop_Testing_Project) – история и архитектура кроссплатформенного GUI-тестирования.  

Эти материалы помогут глубже понять специфику UIA/AT-SPI/JAB и лучшие практики локаторов.
